# Delete-intake confirmation candidate

This is an isolated, unshipped candidate rebased onto commit 506e7ae9cebab49399c5567f07e08dcaa8513c5e. It creates **request intake only**; it does not delete accounts or implement erasure. The original direct authenticated INSERT permits delete intake without any confirmation. API-only checks cannot secure that direct path.

## Release sequence

1. Apply the reviewed intake hardening and `20261102170000_data_rights_confirmation_rpc.sql` after a verified backup, schema/grant inspection, supported PostgreSQL version check and staging acceptance. This first stage installs an authenticated-only security-definer RPC and does **not** change the direct insert policy. Until step 3, the direct bypass still exists. No release is implied by this note.
2. Deploy the API change to **every** serving instance, verify the RPC via real authenticated PostgREST in staging, and drain all old API instances and in-flight calls. The API retains the `/v1/account/data-requests` shape, requires the same exact phrase, passes the JWT-authenticated user context, and fails closed (503) when the RPC is unavailable. It never retries with a direct insert. Merge the route together with the account-privacy branch's `viewerId` response binding.
3. Only after operator verification of step 2, separately review and apply `stage-2-enforce.source-only.sql` from this directory. It intentionally is **not** in `supabase/migrations`; normal pending-migration commands must not enable it ahead of API drain. This blocks all ordinary authenticated direct delete inserts. Old APIs and direct database clients that still perform delete inserts then fail; old export and support inserts remain allowed. Support for old delete writers cannot safely continue while removing that bypass.

The stage-two script wraps its policy replacement in one transaction and takes a table lock. It is a one-time cutover and refuses to replace any preexisting policy bearing either fence name, preserving unrelated safeguards. It fails closed when RLS is disabled; an authenticated or anonymous client can assume a table-owner, superuser or BYPASSRLS role; the expected client grants or RPC dependencies are unsafe; or another permissive INSERT/UPDATE/ALL policy applies through either client, PUBLIC or inherited roles. It checks effective table and column grants, including INSERT, UPDATE, DELETE, TRUNCATE, TRIGGER and REFERENCES. In addition to the export-only permissive INSERT policy, it installs restrictive PUBLIC INSERT and UPDATE fences, so adding a permissive policy alone cannot authorize an unconfirmed delete insert or conversion from export for a non-bypass client. The guard does not modify FORCE RLS; confirmation and cancellation function owners must be able to bypass the resulting RLS and have the table, schema and `auth.uid()` permissions required by their reviewed definitions.

This is a point-in-time catalog check, not proof of RPC bodies, dynamic trigger/default behavior, role grants, client permissions or policies after rollout. Before applying, inspect live callable SECURITY DEFINER functions, triggers, default expressions, sequence permissions, RPC definitions and role memberships. The repository contains the scoped cancellation and confirmation RPCs as named data-request mutators, but hosted functions or dynamic SQL may differ. Run authenticated staging smoke tests for creation, cancellation, export and support, including PostgREST and actual deployed identities, and prevent later RLS-disabling or privilege escalation. Table locking waits for direct writes; plan the maintenance window. Do not confuse local fixtures with a live Supabase catalog check.
4. Monitor for errors and verify old versions cannot be reintroduced before claiming enforcement. A rollback that restores direct delete inserts reopens the bypass; a rollback that disables the RPC while new APIs run makes delete intake unavailable. Neither state should be represented as protected and working.

The database uses `auth.uid()` rather than an actor argument and does not trust an application-supplied user ID. Its JWT assurance depends on the actual Supabase/PostgREST identity path; owner/service SQL principals remain privileged. The database requires the exact phrase and server-computes timestamps and status. Direct authenticated clients must send the phrase to the RPC; it is an explicit confirmation, not a secret. Existing open intake records remain unchanged.

The unique active-request index provides one open delete request per user. Two simultaneous confirmations serialize through the index: one succeeds, the other conflicts. This is not an idempotent submission protocol. If a response is lost, retry can return 409; the user must review the existing requests before any retry. No paid calls, account deletion, migration, deployment, or publication were performed.
